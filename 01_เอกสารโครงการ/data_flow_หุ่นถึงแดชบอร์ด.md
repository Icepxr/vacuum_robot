# ผังการไหลของข้อมูล — จากหุ่น MRC-001 ถึงแดชบอร์ด ARIA

> **29 ก.ย. 2026:** สิ่งที่ตัดสินและทำจริงอยู่ที่ [`design/aria-data-spec-v1.md`](../design/aria-data-spec-v1.md) (F1–F10) — ต่างจากผังนี้ 3 จุด: คนขับเลือกห้อง+ชนิด**ในป๊อปอัพหลังถ่าย** (แทน dropdown ก่อนถ่าย/ปุ่มถ่ายใหม่ `retake_of`) · Pi ส่งผ่าน Edge Function + token (แทน service key) · ส่งแถวก่อนแล้วค่อยส่ง crop

**สร้าง 16 ก.ย. 2026** · ต่อจาก C23 (แยก 2 แอป schema เดียวกัน) · ออกแบบให้**ต่อจากโค้ดที่มีอยู่จริง** ไม่รื้อ — ทุกช่องที่เขียนว่า [มีแล้ว] อ้างไฟล์ที่รันได้วันนี้ · [ต้องเพิ่ม] คือส่วนที่ยังไม่มี · [ยังไม่ตัดสินใจ] รอผู้ใช้ (ตาราง §4)

> ⚠ ตามแผน งานฝั่ง ARIA (ช่วง 5–7) อยู่หลังแข่ง 22 ก.ย. · เอกสารนี้มีไว้ให้**ช่วง 1–4 ที่ทำก่อนแข่ง เก็บข้อมูลในรูปที่ช่วง 5–7 ใช้ได้เลย** ไม่ต้อง migrate (ดู §5)

## 1. รายละเอียดแต่ละช่วง

### ช่วง 0 — ทะเบียนมิเตอร์ ลงไปที่ Pi [ต้องเพิ่ม]

**ปัญหาที่แก้:** วันนี้ `meter_id = null` ทุกแถว และ `meter_type` มาจาก flag `--meter-type` ค่าเดียวทั้งรอบรัน ([meter_reader.py:343](../11_pi5_vision/src/meter_reader.py:343)) → แดชบอร์ดจัดกลุ่มเป็นห้องไม่ได้ และถ้ารอบเดียวถ่ายทั้งน้ำ-ไฟ ประเภทจะผิดครึ่งหนึ่ง

**ออกแบบ:** ARIA เป็นเจ้าของตาราง `meters` · ส่งออกเป็น `meters.json` ไปวางที่ `~/mrc/data/meters.json` บน Pi ตอนอยู่แล็บ (ทาง `scp` — ไม่ต้องมี API เพิ่ม)

```json
{ "registry_version": 3, "exported_at": "2026-09-16T10:00:00+07:00",
  "meters": [
    { "meter_id": "W-204", "room": "204", "type": "water",    "digits": 5, "decimals": 3,
      "waypoint": null, "lift_mm": null },
    { "meter_id": "E-204", "room": "204", "type": "electric", "digits": 5, "decimals": 1,
      "waypoint": null, "lift_mm": null } ] }
```

- `digits`/`decimals` ต่อมิเตอร์ → แทน `expected_digits` กลางใน `roi_config.json` ที่ตอนนี้เป็น `null`
- `waypoint`/`lift_mm` เว้น `null` ได้ในโหมดแมนวล · มีช่องไว้ให้โหมด auto ทีหลัง ไม่ต้องแก้ schema อีก
- `registry_version` ติดไปกับทุกแถวที่หุ่นเขียน → ARIA รู้ว่าแถวไหนถ่ายด้วยทะเบียนเก่า

### ช่วง 1 — ESP32 → Pi [มีแล้ว · ไม่แก้]

`#E,<ms>,CAPTURE_REQ,<n>` → Pi ตอบ `$K,<n>,1` ทันทีที่ภาพลง SD ภายในหน้าต่าง 5 s ([capture_daemon.py](../11_pi5_vision/src/capture_daemon.py) · software_architecture §6.1) · **หุ่นไม่รู้และไม่ต้องรู้ว่าเป็นมิเตอร์ไหน** — `n` เป็นแค่ลำดับครั้ง · ห้ามเพิ่มฟิลด์ตัวตนมิเตอร์เข้าโปรโตคอลนี้ เพราะ ESP32 ไม่มีทะเบียนและไม่ควรมี

### ช่วง 2 — Pi: ถ่าย → OCR → แถวข้อมูล [มีแล้ว 13 ฟิลด์ · ต้องเพิ่ม 4 + crop]

**ใครแปะ `meter_id`:** cockpit `/drive` มี "มิเตอร์ที่เลือกอยู่" (dropdown จาก `meters.json` · หรือปุ่ม "ถัดไป" ไล่ตามลำดับห้อง) · ตอน `CAPTURE_REQ` มาถึง daemon อ่านค่าที่เลือกอยู่แล้วแปะลงแถว · ถ้าไม่มีอะไรถูกเลือก แถวได้ `meter_id = null` เหมือนวันนี้ — **ถ่ายห้ามล้ม** ตามลำดับตัด #2 **[ยังไม่ตัดสินใจ — D1]**

**แถวใน `readings.jsonl` หลังเพิ่ม** (ของเดิม 13 ฟิลด์ใน [meter_reader.py:284](../11_pi5_vision/src/meter_reader.py:284) คงไว้ทั้งหมด):

| ฟิลด์ | เดิม/ใหม่ | ใครใส่ | หมายเหตุ |
|---|---|---|---|
| `local_id` `captured_at` `run_id` `raw_text` `value` `confidence` `image_path` `source` `synced_at` | เดิม | Pi | ไม่แก้ |
| `meter_type` | เดิม | Pi | **เปลี่ยนที่มา**: จากทะเบียนของ `meter_id` ที่เลือก · ถ้าไม่มี fallback เป็น flag เดิม |
| `meter_id` `status` `confirmed_value` | เดิม (C23) | Pi ใส่ `meter_id` · อีก 2 ค่าเป็น `ocr`/`null` เสมอ | หุ่น**ห้าม**เขียน `status`/`confirmed_value` เป็นอย่างอื่น |
| `crop_path` | ใหม่ | Pi | `crops/<id>.jpg` — crop ตาม ROI + ย่อ · สร้างใน thread OCR ไม่ใช่ตอนตอบ `$K` |
| `registry_version` | ใหม่ | Pi | จาก `meters.json` · `null` ถ้าไม่มีทะเบียน |
| `device_id` | ใหม่ | Pi | `MRC-001` — เผื่อมีหุ่นตัวที่ 2 |
| `retake_of` | ใหม่ | Pi | `local_id` ของแถวก่อนหน้าที่คนขับกด "ถ่ายใหม่" · `null` ถ้าถ่ายครั้งแรก |

**ลำดับเวลาในช่วง 2 (ห้ามสลับ):** เฟรม → `images/<id>.jpg` + fsync → **`$K`** → (thread) OCR → `crops/<id>.jpg` → append jsonl + fsync · รูปต้นฉบับ 1080p **อยู่บน Pi ตลอด ไม่อัปโหลด** (ตัดสินแล้วในไฟล์ 20 §20.2b)

### ช่วง 3 — Pi → cockpit บน hotspot [มีแล้ว WS · ต้องเพิ่มปุ่ม]

daemon broadcast แถวใหม่ทาง WebSocket ให้ `/drive` แสดง `value` + crop ทันที (§6.1 เดิม) · **เพิ่มปุ่ม "ถ่ายใหม่"** — สร้างแถวใหม่ที่ `retake_of` ชี้แถวเดิม · **ไม่**แก้แถวเดิม ไม่แตะ `status` (เป็นของผู้ให้เช่า) · ARIA ใช้ "แถวล่าสุดต่อ meter_id ต่องวด" เป็นค่าหลัก แถวที่ถูกถ่ายซ้ำเห็นในประวัติ

ทำไมต้องมีที่นี่: คนขับเห็นรูปเบลอ/เล็งพลาดตอนที่ยังอยู่หน้ามิเตอร์ แก้ได้ในวินาทีนั้น · ถ้าปล่อยให้ผู้ให้เช่าเจอตอนยืนยัน = ต้องส่งหุ่นกลับไปทั้งรอบ

### ช่วง 4 — Pi → Supabase ตอนมีอินเทอร์เน็ต [มีแล้ว 8 ฟิลด์ · ต้องเพิ่ม crop + ฟิลด์ + ตัวเรียก]

ของเดิม: [sync_supabase.py](../11_pi5_vision/src/sync_supabase.py) upsert 8 ฟิลด์ด้วย `resolution=merge-duplicates` บน `local_id` · ส่งเฉพาะแถวที่ `synced_at` ว่าง · เครือข่ายล้ม = หยุดแล้วรอรอบหน้า ข้อมูลในเครื่องครบ — **ตรรกะนี้ดีอยู่แล้ว เก็บไว้**

ต้องเพิ่ม 3 อย่าง:

1. **อัปโหลด crop ก่อน แล้วค่อยส่งแถว** — ต่อแถว: `PUT storage/crops/<local_id>.jpg` (upsert) → ใส่ path ใน payload `crop_path` → upsert แถว · ถ้า crop ล้ม **ส่งแถวไปก่อนโดย `crop_path = null`** แล้วรอบหน้าส่ง crop + PATCH ตาม (ตัวเลขสำคัญกว่ารูป · แดชบอร์ดโชว์ "รูปกำลังมา") · crop ที่อัปแล้วแต่แถวล้ม = ไฟล์กำพร้าไม่มีอันตราย รอบหน้าทับ
2. **payload เพิ่ม** `meter_id` `meter_type`(ที่มาใหม่) `crop_path` `registry_version` `device_id` `retake_of` · **ไม่ส่ง** `status`/`confirmed_value` เลย (ให้ default ฝั่งเซิร์ฟเวอร์ — กันหุ่น upsert ทับค่าที่คนยืนยันไปแล้ว)
3. **ตัวเรียก:** วันนี้เป็นสคริปต์รันมือ → `systemd` timer ทุก 5 นาที · ไม่มีเน็ตก็จบเงียบๆ **[ยังไม่ตัดสินใจ — D2]**

สิทธิ์: **service key ใน env ของ Pi** ตามทางเขียวใน `schema.sql` · anon ไม่มีสิทธิ์อะไรกับตารางนี้

### ช่วง 5 — Supabase: ตารางกลาง [มี `meter_readings` · ต้องเพิ่มตารางฝั่ง ARIA]

```
หุ่นเขียน (service key)          คนเขียนผ่าน ARIA (auth ผู้ให้เช่า + RLS)
──────────────────────          ─────────────────────────────────────────
meter_readings  ◀── trigger ─┐  meters          (meter_id, room, type, digits, decimals, waypoint, lift_mm,
  + crop_path                │                   installed_at, retired_at, start_value, end_value)
  + registry_version         │  rooms           (room, floor, note)
  + device_id                │  tenants         (room, name, email, moved_in, moved_out, start_water, start_electric)
  + retake_of                │  rates           (type, baht_per_unit, effective_from, effective_to)   append-only
                             │  billing_cycles  (cycle, cutoff_date, state)
reading_events ──────────────┘  invoices        (cycle, room, tenant, water_units, electric_units, amount, state)
  (reading_id, event,           invoice_emails  (invoice_id, to, sent_at, message_id, error)
   confirmed_value, by, at, note)
```

- **`reading_events` เป็น append-only ที่แท้จริง** (ทุกการยืนยัน/แก้/ปฏิเสธ/ผูกห้อง = 1 แถวใหม่) · คอลัมน์ `status`/`confirmed_value` บน `meter_readings` เป็น **cache ของ event ล่าสุด** อัปเดตด้วย trigger ไม่ให้แอปเขียนตรง **[ยังไม่ตัดสินใจ — D3]**
- `meters` มี `installed_at`/`retired_at`/`start_value`/`end_value` → รองรับ "เปลี่ยนมิเตอร์ใหม่" (ห้องหนึ่งมีหลาย `meter_id` ตามเวลา) ตาม mockup หน้า 4 · **`meter_id` = ตัวมิเตอร์ ไม่ใช่ห้อง** — ต่างจากคอมเมนต์ใน `schema.sql` ("ผูกห้อง/มิเตอร์") เล็กน้อย ต้องเลือกให้ชัดตอนสร้างตาราง
- กติกาที่บังคับด้วย constraint ไม่ใช่ UI: `confirmed_value ≥ ค่ายืนยันล่าสุดของ meter_id เดียวกัน` (ยกเว้นแถวแรกหลัง `installed_at`) · `rates.effective_from` ต้องเป็นวันตัดรอบในอนาคต ณ เวลา insert

### ช่วง 6 — ARIA web อ่าน/เขียน [ต้องสร้าง]

- **อ่าน:** view ต่อหน้า — `v_cycle_status` (หน้าหลัก) · `v_confirm_queue` (แถวล่าสุดต่อ meter_id ต่องวด ที่ `status='ocr'` · เรียง ผิดปกติ → conf ต่ำ → ปกติ) · `v_invoice_draft` (`confirmed_value` งวดนี้ − งวดก่อน × `rates` ที่ `effective_from ≤ cutoff < effective_to`)
- **เขียน:** insert `reading_events` · insert `rates` · insert `invoices` เมื่อยืนยันครบ 2 มิเตอร์ + มีอีเมล · **ห้ามแอปเขียน `meter_readings` ตรง**
- "ดูรูปเต็ม" ใช้ได้เฉพาะเมื่อ Pi อยู่เครือข่ายเดียวกัน (`http://mrc.local/images/<id>.jpg`) — ปุ่มโชว์ "Pi ไม่ออนไลน์" ถ้าไม่ถึง · crop จาก Storage ดูได้เสมอ

### ช่วง 7 — ส่งอีเมล [ต้องสร้าง · auth ยังไม่ตัดสิน]

- รันฝั่งเซิร์ฟเวอร์ (Edge Function / worker) ไม่ใช่ในเบราว์เซอร์ — เบราว์เซอร์ปิดกลางทางแล้วส่งครึ่งเดียวไม่ได้
- ลูป: อ่าน `invoices` ที่ `state='ready'` และถูกเลือก → ต่อฉบับ: ส่ง → insert `invoice_emails` → หน่วง 2–5 s (ไฟล์ 20 §20.4) → ฉบับถัดไป · ล้มฉบับไหนบันทึก `error` แล้วไปต่อ ไม่หยุดทั้งชุด
- แนบ crop 2 รูป/ฉบับ ไม่แนบต้นฉบับ (ขนาดดู ไฟล์ 20 §20.7)
- วิธีล็อกอิน Gmail **[ยังไม่ตัดสินใจ — D4]**

## 2. เมื่ออะไรพัง — ข้อมูลไปอยู่ไหน

| เหตุการณ์ | ผล | ทำไมไม่เสียข้อมูล |
|---|---|---|
| ไม่มีเน็ตที่สนาม (ปกติ) | แถว+รูปกองบน SD | ช่วง 4 ส่งเฉพาะ `synced_at` ว่าง · SD พอ ~23 ปีที่ 100 ห้อง (ไฟล์ 20 §20.2b) |
| ไฟดับระหว่างเขียน jsonl | แถวสุดท้ายอาจขาด | fsync ไฟล์+directory มีแล้ว ([meter_reader.py:302](../11_pi5_vision/src/meter_reader.py:302)) · รูปลง SD ก่อนแถวเสมอ → อย่างแย่คือ "มีรูป ไม่มีแถว" กู้ได้ด้วยรัน OCR ซ้ำจากโฟลเดอร์ |
| sync ซ้ำ / รันสองรอบชนกัน | ไม่มีแถวซ้ำ | `local_id` unique + upsert merge-duplicates (มีแล้ว) |
| crop ขึ้นแล้ว แถวล้ม | ไฟล์กำพร้าใน Storage | รอบหน้า upsert ทับ path เดิม · ไม่มีผลกับบิล |
| แถวขึ้นแล้ว crop ล้ม | `crop_path=null` | แดชบอร์ดโชว์ "รูปกำลังมา" · รอบหน้า PATCH ตาม |
| หุ่น upsert ทับแถวที่คนยืนยันแล้ว | **ไม่เกิด** | payload ไม่มี `status`/`confirmed_value` · ค่าจริงอยู่ใน `reading_events` |
| ถ่ายโดยไม่ได้เลือกมิเตอร์ | `meter_id=null` | แดชบอร์ดมีถัง "ยังไม่ผูกห้อง" ให้ผู้ให้เช่าผูกทีหลัง (event `assigned`) — ถ่ายไม่ล้ม |
| ทะเบียนบน Pi เก่า | `registry_version` ต่ำกว่าปัจจุบัน | ARIA ติดป้าย "ถ่ายด้วยทะเบียนรุ่นเก่า" · ค่าไม่เสีย |
| นาฬิกา Pi เพี้ยน | `captured_at` เพี้ยน | มี `created_at` ฝั่งเซิร์ฟเวอร์เป็นเวลาที่สอง · **ยังไม่ยืนยันว่า Pi ตั้งเวลาจากอะไรตอนไม่มีเน็ต [D5]** |

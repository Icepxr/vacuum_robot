## ภาพรวมลำดับเฟส (Roadmap)

| เฟส | เนื้อหา | ขึ้นกับ | ผลลัพธ์ที่ต้องได้ |
|---|---|---|---|
| **A** | ทดสอบอุปกรณ์แยกทีละตัว (bench test) — หัวข้อ 1.2–1.5 | อุปกรณ์ครบ (มีแล้ว) | สเปกจริงของแต่ละมอเตอร์/กลไก (แรงบิด, กระแส, ประสิทธิภาพ) |
| **B** | ทำ pin mapping + wiring diagram + firmware ระดับล่างของ ESP32 | ผล A (รู้ต้องต่อวงจรแบบไหน กระแสเท่าไหร่) | วงจรต่อจริงได้ ไม่ลัดวงจร ไม่มอเตอร์ไหม้ |
| **C** | ออกแบบ System Program (FSM) + integration test รวมระบบ | ผล A+B | หุ่นวิ่ง+ทำความสะอาด+ยกกล้องได้ตามกติกาความปลอดภัย |
| **D** | Simulation (โครงสร้าง + พลังงาน) โดยใช้ค่าจริงจาก A/C มา calibrate | ผล A, C (บางส่วน) | กราฟ/ตัวเลขเชิงวิศวกรรมสำหรับเขียนรายงาน |
| **E** | ทดสอบความทนทาน (endurance) + สรุปเขียนรายงาน | ผล A–D | ข้อมูลครบสำหรับรายงานวิศวกรรมฉบับสมบูรณ์ |

A และ B ทำคู่ขนานกันได้ (ทดสอบมอเตอร์ตัวไหนเสร็จ ก็ต่อวงจรตัวนั้นได้เลย) ส่วน D ควรรอผลจาก A บางส่วนก่อน เพราะ simulation ที่ใช้ตัวเลขจริงจากการวัด จะน่าเชื่อถือกว่าใช้ datasheet เฉยๆ มาก

## 1. แผนทดสอบประสิทธิภาพอุปกรณ์ (Test Plan)

หลักการ: ทดสอบจาก**ล่างขึ้นบน** (bottom-up V&V) — ชิ้นเดี่ยวบนโต๊ะก่อน → ประกอบเป็นระบบย่อยบนตัวหุ่น → รวมทั้งระบบ แต่ละการทดสอบต้องมี **Objective / Setup / วิธีวัด / เกณฑ์ผ่าน (pass criteria)** ที่ชัดเจน ไม่ใช่แค่ "ลองแล้วดูว่าโอเคไหม" เพราะต้องเอาตัวเลขไปใช้ต่อใน simulation (หัวข้อ 2)

### 1.1 ทดสอบมอเตอร์ดูดฝุ่น (Suction)

| รายการ | รายละเอียด |
|---|---|
| Objective | หาแรงดูด (suction pressure), อัตราการไหลอากาศ, กระแสไฟที่ใช้จริง |
| Setup | ตั้งมอเตอร์+ใบพัดบนแท่นทดสอบ ต่อท่อเข้ากับ manometer แบบหลอด U (วัดแรงดันเป็น mmH₂O) ต่อ multimeter/current sensor คร่อมสาย |
| วิธีวัด | (1) วัดแรงดันขณะปิดปลายท่อสนิท (static pressure) (2) วัดกระแสตอน stall vs free-run (3) ทดสอบเก็บฝุ่นจริง: โรยเศษวัสดุมาตรฐาน (ข้าวสาร/ทราย/เส้นผม) น้ำหนักที่ชั่งไว้ก่อน ดูดแล้วชั่งซ้ำ = % ประสิทธิภาพเก็บ |
| เกณฑ์ผ่าน | กระแสไม่เกินที่ไดรเวอร์/BMS รับได้ (เทียบกับ BMS 4S ที่มี), เก็บฝุ่นทดสอบได้ ≥ 80% บนพื้นเรียบ |
| ทำไมต้องทำ | ตัวเลขนี้ใช้ต่อในงบพลังงาน (2.2) และเป็นข้อมูลอ้างอิงเทียบ BLDC เฟส 2 ในอนาคต |

### 1.2 ทดสอบการขับเคลื่อน (Locomotion)

| รายการ | รายละเอียด |
|---|---|
| Objective | ตรวจความแม่นยำ odometry, แรงบิด/ความเร็วจริง, ความสามารถข้ามสิ่งกีดขวาง |
| วิธีวัด | (1) วิ่งระยะที่กำหนด (เช่น 1 m ตรง, หมุน 360°) เทียบกับที่วัดจริงด้วยตลับเมตร/มุมองศา = คำนวณ error % ของ encoder (2) ทดสอบขึ้นธรณีประตู/พรมหนาที่ระบุไว้ในรายงาน scissor (ต้องพับเสาก่อน) — วัดความสูงสูงสุดที่ข้ามได้ (3) วัดกระแสขณะวิ่งปกติ vs กระแส stall (ล้อติด) (4) ทดสอบ cliff sensor และ bumper แยกจากมอเตอร์ (ตอบสนองถูกต้องหรือไม่) |
| เกณฑ์ผ่าน | error odometry ที่ยอมรับได้สำหรับ mapping ในเฟส 2 (ควร <5%), ไม่มี stall เกิน 2–3 วินาทีติดโดยไม่ตัดไฟป้องกันมอเตอร์ไหม้ |

### 1.3 ทดสอบกลไกปัดกวาด (Cleaning)

| รายการ | รายละเอียด |
|---|---|
| Objective | ประสิทธิภาพเก็บฝุ่นตามขอบ/มุม จากแปรงข้าง (มอเตอร์เหลือง) |
| วิธีวัด | ทดสอบแยกแปรงอย่างเดียวก่อน (ไม่มีดูด) ดูรูปแบบการปัดเศษ จากนั้นทดสอบร่วมกับมอเตอร์ดูด บนพื้น 2–3 แบบ (กระเบื้อง, พรมบาง, ไม้) ชั่งเศษก่อน-หลัง |
| เกณฑ์ผ่าน | เก็บเศษตามขอบผนัง/มุมห้องได้ (จุดที่แปรงกลางเก็บไม่ถึง) โดยไม่ทำให้เศษกระเด็นออกนอกเส้นทางหุ่น |

### 1.4 ทดสอบกลไก Scissor Lift ยกกล้อง

อ้างอิงจากรายงาน `scissor_lift/README.md` ที่คำนวณไว้แล้ว งานนี้คือ**เอาของจริงมาเทียบกับตัวเลขที่คำนวณ**:

| รายการ | ต้องวัดอะไร | ค่าที่คำนวณไว้ (อ้างอิง) |
|---|---|---|
| เวลายก/พับ | จับเวลาจริงเทียบ 3 วิที่ตั้งไว้ | 3 s (57°/s) |
| กระแสเซอร์โว | วัดขณะยก โดยเฉพาะช่วงพีคใกล้จุดพับสุด | พีค 0.91 A @ 6V |
| **การแกว่งปลายเสา** | วัดระยะแกว่งจริงตอนยกสุดแล้วหยุด (ใช้ dial gauge หรือกล้อง slow-mo วัด) | คาดการณ์ ±9.3 mm ⚠ **ความเสี่ยงอันดับ 1 ตามรายงาน** |
| Repeatability | ยก-พับซ้ำ 20–30 รอบ วัดตำแหน่งปลายสุดว่าคลาดเคลื่อนสะสมไหม | — |
| Self-lock | ตัด PWM ตอนยกสุดแล้ว ลองกดปลายเบาๆ ดูว่ากลไกล็อกจริงไหม | ออกแบบให้ล็อกตัวเองที่จุดตายตัว |
| เวลานิ่งก่อนถ่ายภาพ | วัดว่าแกว่งจนนิ่งใช้เวลากี่วินาที (มี natural freq ~12 Hz เป็นตัวตั้งต้น) | ต้องหยุดนิ่ง 1–2 วิ ก่อนถ่าย/สแกน |

ถ้าแกว่งเกินรับได้ตามที่รายงานเตือนไว้ ให้ทำตามมาตรการที่ระบุไว้แล้ว (บูชทองเหลือง/ไนลอนทุกจุดหมุน + แกนขวางทุกชั้น) **ก่อน** ไปทดสอบข้อถัดไป เพราะถ้าเสาแกว่งมาก ภาพจากกล้องจะเบลอ ทำให้ทั้งระบบใช้งานจริงไม่ได้

### 1.5 ทดสอบรวมทั้งระบบ (System Integration Test)

ทำ**หลังสุด** เมื่อ 1.1–1.4 ผ่านแยกกันแล้วเท่านั้น:

1. **Power budget รวม** — เดินทุกระบบพร้อมกัน (ขับ+ดูด+แปรง) วัดกระแสรวม เทียบกับความจุแบต 4S ที่มี
2. **Mission test เต็มรูปแบบ** — จำลองงานจริง: วิ่งสุ่ม+ดูด+ปัด แล้วสั่งยกกล้องเป็นระยะ ตรวจว่ากติกาที่กำหนดไว้ในรายงาน (ห้ามยกขณะเคลื่อนที่, จำกัดความเร่งขณะเสายก ≤4.9 m/s² ฯลฯ) ถูกบังคับใช้จริงในซอฟต์แวร์
3. **Endurance test** — วิ่งต่อเนื่องจนแบตหมด จับเวลา รวมถึงเช็คอุณหภูมิมอเตอร์/ตัวควบคุมไฟ (buck converter) ว่าร้อนผิดปกติไหม
4. **Safety test** — cliff sensor หยุดหุ่นก่อนตกจริงไหม, bumper ตอบสนองไว พอไหม

## 2. แผน Simulation

เป้าหมายคือได้ตัวเลข**เชิงปริมาณ**ใส่รายงานวิศวกรรม ไม่ใช่แค่คำนวณมือ สิ่งสำคัญคือ simulation ควร**ป้อนกลับด้วยค่าที่วัดได้จริงจากข้อ 1** ไม่ใช่ใช้แค่ datasheet — งานนี้จะน่าเชื่อถือกว่ามาก

### 2.1 Simulation การรับแรง/โครงสร้าง (Structural)

- **ฐานหุ่น** — งานค้างจาก `base_strength_report.md`: ไฟล์ `Base1.1.f3d` เตรียม Simulation Study ไว้แล้วแต่ยังไม่ได้รัน Static Stress จริงใน Fusion 360 (ตอนนี้มีแค่ hand-calc ด้วย beam theory) ขั้นตอนรันมีอยู่ในรายงานแล้ว (§4) แนะนำให้รันเทียบกับตารางที่คำนวณไว้ — ถ้าตรงกันแปลว่า model สอดคล้อง ถ้าไม่ตรงให้เชื่อค่า Fusion
- **แขน Scissor lift** — ยังไม่มี FEA ของชิ้นแขน/หมุด แนะนำจำลองที่ **มุมพับสุด** (จุดที่แรงในแขนสูงสุดตามที่คำนวณ 86.9 N ก่อนมีสปริง / 15.3 N หลังมีสปริง) เพื่อตรวจความเค้นที่รูหมุดและความหนาแขน 10 mm (ที่ลดจาก 14mm ตอนแก้บั๊กชนกัน) ว่ายังพอสำหรับความเค้นสัมผัส (bearing stress) ที่รู
- **การพลิกคว่ำ** — มี worst-case แบบ static อยู่แล้ว (12.2 m/s² ตอนเสายกสุด) ถ้าต้องการรายงานที่ดูสมจริงขึ้น ทำ motion simulation ง่ายๆ ใน Fusion (หรือ Python) จำลองตอนเบรกกะทันหันพร้อมเสายกอยู่ เทียบ CoG dynamic vs static

### 2.2 Simulation พลังงานที่ใช้ในแต่ละการทำงาน

แนะนำสร้างเป็นตาราง/โมเดล duty-cycle ของแต่ละโหมด แล้วคำนวณพลังงานรวม:

| โหมด | ระบบที่ทำงาน | กระแสประมาณ (จากข้อ 1) | ใช้เมื่อไหร่ |
|---|---|---|---|
| Standby | Pi5+ESP32 เท่านั้น | วัดจากทดสอบ | รอคำสั่ง |
| วิ่งเปล่า | มอเตอร์ขับ 2 ตัว | จากทดสอบ 1.2 | สำรวจพื้นที่ |
| ทำความสะอาดเต็มระบบ | ขับ+ดูด+แปรง | จากทดสอบ 1.1–1.3 | โหมดหลัก |
| ยก/พับกล้อง | เซอร์โว MG996R | 0.91 A พีค (คำนวณไว้แล้ว) | เป็นช่วงสั้นๆ |
| Worst-case พร้อมกัน | ทุกระบบ | ผลรวม | ใช้ sizing แบต/BMS |

จากตารางนี้คำนวณ **energy budget**: ความจุแบต (Ah ของแพ็ค 18650 4S ที่มี) ÷ กระแสเฉลี่ยตามสัดส่วนเวลาที่ใช้แต่ละโหมดจริง (เช่น ทำความสะอาด 70% ของเวลา, ยกกล้อง 5%, วิ่งเปล่า 25%) = **เวลาทำงานต่อการชาร์จ 1 ครั้ง (runtime)** แล้วเทียบกับที่วัดได้จริงจาก endurance test (1.5 ข้อ 3) — ถ้าตัวเลขจากโมเดลกับของจริงต่างกันมาก ต้องหาว่าประเมินอะไรผิด (มักเป็นค่า stiction/แรงเสียดทานจริงที่สูงกว่าคำนวณ เหมือนที่เจอในรายงาน scissor)

ผมสร้างสคริปต์ Python ให้คำนวณตารางนี้อัตโนมัติได้ทันทีที่มีตัวเลขจากการทดสอบจริง (ใส่ค่ากระแส/เวลาแต่ละโหมด ออกมาเป็นกราฟ+ตัวเลข runtime) — บอกได้เลยถ้าอยากให้เตรียมให้ตอนนี้

## 3. Wiring Diagram

ก่อนวาดวงจรจริง ต้องทำ 2 อย่างนี้ก่อน (เป็นขั้นตอนมาตรฐานงาน EE: ทำตาราง pin mapping / ICD ก่อนวาด schematic):

### 3.1 สิ่งที่ต้องกำหนดก่อนวาด

1. **ตาราง pin mapping ของ ESP32-S3** — กำหนดว่า GPIO ไหนต่อกับอะไรบ้าง: PWM มอเตอร์ขับ 2 ช่อง (ผ่าน TB6612FNG), encoder 2 ตัว (interrupt pins), I2C สำหรับ MPU6050, digital in สำหรับ cliff sensor 3 ตัว + bumper 3 ตัว, PWM/digital out สำหรับ MOSFET IRF520 คุมมอเตอร์ดูด+แปรง, PWM สำหรับเซอร์โว MG996R, UART สำหรับคุยกับ Pi5
2. **แผนผังการจ่ายไฟ (power tree)** — แบต 4S 18650 → BMS → แยกเป็น 2 สาย: (ก) ตรงเข้ามอเตอร์กำลัง/เซอร์โว ผ่าน MOSFET/ไดรเวอร์ (ข) ผ่าน buck 5V/5A เลี้ยง Pi5 (แยกตัวนี้จากราง logic เด็ดขาดตามที่รายงาน scissor เตือนไว้) และผ่าน buck แยกอีกตัวเลี้ยง ESP32+เซนเซอร์ พร้อม**กราวด์ร่วมจุดเดียว (star ground)** และ**ตัวเก็บประจุ 1000 µF ที่ขั้วเซอร์โว**ตามที่ระบุในรายงาน

### 3.2 สิ่งที่ไดอะแกรมต้องมีครบ

- Power tree (แบต → BMS → buck ต่างๆ → โหลดแต่ละตัว พร้อม fuse/switch)
- Signal tree (ESP32 ↔ เซนเซอร์/มอเตอร์ไดรเวอร์/เซอร์โว ทุกเส้น พร้อมเลข GPIO)
- เส้นเชื่อม ESP32 ↔ Pi5 (USB serial ตามที่ระบุใน BOM)
- หมายเหตุจุดวิกฤต: แยกกราวด์/แยก BEC เซอร์โว, ตำแหน่งตัวเก็บประจุ

### 3.3 ขั้นตอนถัดไป

แนะนำให้ทำตาราง pin mapping (ข้อ 3.1.1) ก่อน — พอมีตารางนั้นแล้ว ผมสามารถช่วยวาด wiring diagram ให้เป็นภาพ (schematic-style) ได้ทันที ถ้ายังไม่ได้กำหนด pin ผมช่วยร่างตารางเริ่มต้นให้ตาม BOM เฟส 1 ที่มีอยู่ก่อนก็ได้ บอกได้เลยว่าอยากให้เริ่มจากตรงไหน

## 4. ออกแบบ System Program (Software Architecture)

ยังไม่ได้ออกแบบเลย — นี่คืองานที่มีผลกับทุกหัวข้อข้างบน (ต้องรู้ pin mapping จากข้อ 3 และกติกาความปลอดภัยจากข้อ 1.4 มาก่อน)

### 4.1 การแบ่งงานระหว่าง ESP32 กับ Pi5

ตามที่ระบุไว้ใน BOM เฟส 1 อยู่แล้ว: **ESP32-S3 = งานเรียลไทม์** (คุมมอเตอร์/อ่านเซนเซอร์ตรงๆ, ต้อง latency ต่ำ) **Pi5 = สมอง** (ตัดสินใจระดับสูง, เฟส 2 จะเพิ่ม SLAM/vision) คุยกันผ่าน USB serial — หลักการนี้ถูกต้องแล้ว แค่ต้องออกแบบรายละเอียดต่อ

### 4.2 ออกแบบ Finite State Machine (FSM) — แกนหลักของระบบ

ตัวอย่างสถานะที่ควรมี (ปรับตามภารกิจจริง):

```
IDLE → EXPLORE_CLEAN → OBSTACLE_AVOID ─┐
              │            (กลับ)      │
              ├──→ CLIFF_STOP (หยุดฉุกเฉิน)
              ├──→ CAMERA_LIFT_SEQUENCE
              │      (บังคับ v=0 ก่อนเข้า state นี้เท่านั้น)
              └──→ LOW_BATTERY → RETURN/STOP
```

กติกาที่ **ต้อง hard-code เป็นเงื่อนไข transition** ของ state machine (ดึงมาจากรายงาน scissor โดยตรง ไม่ใช่แค่คำแนะนำ):
1. เข้า `CAMERA_LIFT_SEQUENCE` ได้เมื่อ v = 0 เท่านั้น
2. ขณะอยู่ใน state นี้ ต้อง clamp คำสั่งเร่ง/เบรกไม่เกิน 4.9 m/s²
3. จำกัดความเร็วหมุนตัวขณะเสายกอยู่ (แรงหนีศูนย์)
4. ต้องกลับ state พับเสาก่อนเข้าธรณีประตู/พรมหนา (ต้องมีเซนเซอร์หรือ mapping รู้ตำแหน่งเหล่านี้)
5. ถ่ายภาพ/สแกนหลังหยุดนิ่งแล้ว 1–2 วินาที (ใช้ผลวัดจริงจากข้อ 1.4)

### 4.3 Protocol การสื่อสาร ESP32 ↔ Pi5

ต้องออกแบบ message format ง่ายๆ ก่อนเริ่มเขียนโค้ด เช่น:
- Pi5 → ESP32: คำสั่งความเร็ว/ทิศทาง, คำสั่งเปิด-ปิดมอเตอร์ดูด/แปรง, คำสั่งยก/พับกล้อง
- ESP32 → Pi5: สถานะเซนเซอร์ทั้งหมด (encoder, IMU, cliff, bumper), สถานะแบต, ยืนยันว่า state ปัจจุบันคืออะไร (สำคัญมาก เพื่อให้ Pi5 รู้ว่าตอนนี้ยกกล้องอยู่หรือเปล่าก่อนสั่ง)
- แนะนำ format ง่ายๆ แบบ text line (CSV หรือ key=value) ผ่าน serial ก็เพียงพอสำหรับเฟส 1 ยังไม่ต้องซับซ้อนแบบ ROS

### 4.4 ลำดับการพัฒนาซอฟต์แวร์ที่แนะนำ

1. เขียน driver ระดับล่างบน ESP32 ทีละตัว (มอเตอร์ขับ, encoder, เซนเซอร์, เซอร์โว) — ทดสอบคู่กับข้อ 1 ไปพร้อมกันเลย
2. ประกอบเป็น FSM บน ESP32 (ยังไม่ต้องมี Pi5) ให้หุ่นวิ่งสุ่ม+ดูดได้เองตามที่ BOM เฟส 1 ตั้งเป้าไว้
3. เพิ่ม serial link คุยกับ Pi5 (ตอนนี้ Pi5 แค่ monitor/สั่งเปิด-ปิดเฉยๆ)
4. ค่อยขยาย Pi5 ให้ตัดสินใจแทน ESP32 บางส่วน เตรียมพร้อมสำหรับเฟส 2 (SLAM)

## สรุป: 3 ขั้นถัดไปที่ควรเริ่มทันที

1. **แก้ปัญหาการแกว่งของเสา scissor lift** (บูช + แกนขวาง) แล้วincode ทดสอบตามข้อ 1.4 — เป็นความเสี่ยงอันดับ 1 ที่ค้างอยู่จากรายงานเดิม ควรปิดจุดนี้ก่อนไปยุ่งกับส่วนอื่น
2. **ทำตาราง pin mapping ของ ESP32** (ข้อ 3.1) — เป็นจุดตั้งต้นของทั้ง wiring diagram และ system program พร้อมกัน
3. **ทดสอบมอเตอร์แยกทีละตัวบนโต๊ะ** (ข้อ 1.1–1.3) — เก็บตัวเลขกระแส/แรงจริงไว้ใช้ทั้งใน wiring (เลือกขนาดสาย/ฟิวส์) และ simulation พลังงาน (ข้อ 2.2)

บอกได้เลยว่าอยากให้ช่วยเริ่มจากจุดไหนก่อน เช่น ร่างตาราง pin mapping, เขียนสคริปต์คำนวณ energy budget, หรือช่วยออกแบบ FSM ละเอียดขึ้น

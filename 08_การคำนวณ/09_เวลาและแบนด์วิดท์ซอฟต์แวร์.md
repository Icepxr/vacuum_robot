## 9.1 ⭐ ห้ามคำนวณความเร็วจากหน้าต่าง 10 ms — quantization error

**ปัญหา:** `T_Control` ทำงานที่ 100 Hz (คาบ 10 ms) แต่ที่ความเร็วเป้าหมาย 0.15 m/s:

```
ระยะทางใน 1 tick = 0.15 m/s × 0.010 s = 1.5 mm
counts ใน 1 tick  = 1.5 mm / 0.11475 mm/count = 13.1 counts

ความคลาดเคลื่อนจากการปัดเศษ ±1 count:
error = 1 / 13.1 = ±7.6%
```

**ผลกระทบ:** เทอม D ของ PID จะกระโดดตามสัญญาณรบกวนนี้ ทำให้มอเตอร์กระตุก

**ทางแก้ที่ล็อกไว้:**
```
รัน PID ที่ 100 Hz ตามเดิม แต่คำนวณความเร็วจากหน้าต่างย้อนหลัง 30 ms:
counts ใน 30 ms = 39.2 counts  →  error = 1/39.2 = ±2.6%   ✓
```
หรือใช้ moving average 3 tick (ผลเทียบเท่ากัน)

| หน้าต่าง | counts ที่ 0.15 m/s | quantization error |
|---|---:|---:|
| 10 ms | 13.1 | ±7.6% ✗ |
| **30 ms** | **39.2** | **±2.6% ✓** |

> อัปเดต 13 ก.ย. 2026 จากล้อ Ø65 → Ø90 mm ตามไฟล์ 01 §1.4; ค่าชุดเดิม 18.1/54.3 counts และ ±5.5/±1.8% ถูกแทนที่แล้ว

## 9.2 ตารางงาน FreeRTOS และเหตุผลของลำดับความสำคัญ

| Task | Core | คาบ | Prio | หน้าที่ |
|---|---|---|---|---|
| `T_Safety` | 1 | 5 ms (200 Hz) | **6 สูงสุด** | stall (G5) · แรงดันแบต · watchdog สื่อสาร → บังคับ `brake()` ได้ทันที |
| `T_Control` | 1 | 10 ms (100 Hz) | 5 | PCNT → ความเร็ว → PID → LEDC · odometry |
| `T_Sensor` | 0 | 20 ms (50 Hz) | 4 | HC-SR04 · ADC แบต/กระแสเซอร์โว |
| `T_Behavior` | 0 | 50 ms (20 Hz) | 3 | FSM tick → setpoint ลง queue |
| `T_Comm` | 0 | 50 ms (20 Hz) | 2 | telemetry ขึ้น Pi5 · parse คำสั่ง |
| `T_Display` | 0 | 100 ms (10 Hz) | 1 | วาดจอ TFT |

### ทำไมจอต้อง priority ต่ำสุด — ตัวเลขที่บังคับ

```
GC9A01 240 × 240 px × 2 bytes/px = 115,200 bytes = 115 kB ต่อเฟรมเต็ม
```
ถ้าวาดทั้งจอบ่อยๆ SPI DMA จะแย่งบัสและเวลา CPU กับ PID loop
→ **วาดเฉพาะส่วนที่ค่าเปลี่ยน (dirty rectangle) ที่ 10 Hz** ไม่ใช่ล้างจอใหม่ทุกเฟรม

### ทำไมใช้ PCNT ไม่ใช่ ISR

```
7,310 counts/s ต่อล้อ × 2 ล้อ = 14,620 interrupt/s ถ้าใช้ ISR
```
→ กิน CPU ฟรีๆ และนับพลาดตอน CPU ยุ่ง · PCNT นับด้วยฮาร์ดแวร์ ไม่พลาด ไม่กิน CPU
**แต่ต้องตั้ง watch point กันตัวนับ 16 บิตล้นภายใน 4.48 s** (ดูไฟล์ 01 §1.5)

## 9.3 HC-SR04 — ข้อจำกัดเชิงเวลา

| ข้อ | ตัวเลข | เหตุผล |
|---|---|---|
| **ห้ามใช้ `pulseIn()`** | บล็อกได้นานถึง **38 ms** ต่อครั้ง | ต้องใช้ interrupt จับขอบขึ้น/ลงของ ECHO แล้วอ่านเวลาจาก `esp_timer_get_time()` |
| เว้นระยะระหว่าง ping | **≥ 60 ms** | ไม่งั้นเสียงสะท้อนรอบก่อนปนรอบใหม่ |
| ยิงพร้อมกัน 2 ตัว | ทำได้ (แยกขา ECHO) | ถ้าลำคลื่นซ้อนกันมาก ให้สลับยิงทีละตัว → 25 Hz ต่อตัว ยังพอ |

`T_Sensor` ที่ 50 Hz (20 ms) เร็วกว่าข้อจำกัด 60 ms → **ต้องยิง ping ทุก 3 รอบของ task** ไม่ใช่ทุกรอบ

## 9.4 การจัดสรร LEDC (8 channel / 4 timer)

| Timer | ความถี่ | Resolution | Channel |
|---|---|---|---|
| T0 | 20 kHz | 11-bit | ch0–ch3 มอเตอร์ล้อ 2 ตัว (ตัวละ 2 ช่อง) |
| T1 | 20 kHz | 10-bit | ch5 แปรงอย่างเดียว |
| T2 | **50 Hz** | 16-bit | ch6 เซอร์โว A · ch7 เซอร์โว B |
| T3 | 25 Hz | 10-bit | ch4 blower — **ใช้เฉพาะถ้าจะคุมความเร็ว** |

**ใช้ 7/8 ช่อง** เพราะ blower เป็น GPIO เปิด-ปิดธรรมดา ไม่ผูก LEDC (เหตุผลเชิงความร้อน — ดูไฟล์ 04)

> **ข้อแลกเปลี่ยนที่ต้องจำ:** ถ้าเฟส 2 จะเพิ่มแปรงกลาง ให้ใช้ GPIO เปิด-ปิดธรรมดา (แปรงลูกกลิ้งหมุนความเร็วคงที่) หรือแชร์ช่องกับมอเตอร์ดูด

## 9.5 แบนด์วิดท์ลิงก์ ESP32 ↔ Pi 5

```
telemetry 20 Hz × ~90 ตัวอักษร = 1,800 B/s
115200 baud ÷ 10 bit/byte (8N1) = 11,520 B/s
headroom = 11,520 / 1,800 = 6.4 เท่า   ✓
```
**Baud 115200 เพียงพอ** — ถ้าอนาคตต้องส่งภาพหรือ log หนาขึ้น ค่อยขยับเป็น 460800

**สามอย่างที่ต้องทำ ไม่งั้นลิงก์ไม่ติด:**

| # | ฝั่ง | ทำอะไร |
|---|---|---|
| 1 | Pi 5 | `enable_uart=1` ใน `/boot/firmware/config.txt` และ **ลบ `console=serial0,115200` ออกจาก `cmdline.txt`** · อุปกรณ์คือ `/dev/ttyAMA0` (Pi 5 ไม่ใช่ `ttyS0`) |
| 2 | ESP32 | **flash ผ่านช่อง USB native (GPIO 19/20) เท่านั้น** — ถ้า flash ผ่านช่อง UART ชิปแปลงสัญญาณจะแย่งขา 43/44 |
| 3 | Pi 5 | parser ต้อง**ทิ้งบรรทัดที่ไม่ขึ้นต้นด้วย `#`** เพราะ ROM bootloader ของ ESP32 พ่น boot log ออก UART0 ทุกครั้งที่รีเซ็ต |

**ไม่ต้องมี level shifter** — ทั้งสองฝั่งเป็นลอจิก 3.3 V

## 9.6 งบขา GPIO ของ ESP32-S3 N16R8

```
ขาใช้ได้จริง 25 ขา: GPIO 1, 2, 4–18, 21, 38–42, 47, 48
ขาที่ใช้ไม่ได้แม้โผล่ที่ header:
  26–32  = SPI Flash
  33–37  = Octal PSRAM (ส่วน "R8" ของชื่อรุ่น)
  0/3/45/46 = strapping pin
  19/20  = USB native
  43/44  = UART0 (ตอนนี้เป็นสายไป Pi 5 ถาวร)
```

| ทางเลือกไดรเวอร์ | จอ TFT อยู่ที่ | ขาที่ใช้ | ผล |
|---|---|---:|---|
| TB6612FNG | Pi 5 | 23 / 25 | เหลือ 2 |
| TB6612FNG | ESP32 | 29 / 25 | **เกิน 4** ✗ |
| **DRV8871 ×2** | **ESP32** | **24 / 25** | **เหลือ 1** ✓ ← เลือก |
| DRV8871 ×2 | Pi 5 | 20 / 25 | เหลือ 5 |

**เทคนิคประหยัดขาจอ (จาก 6 → 4 ขา):** ผูก `RST` เข้าขา EN ของบอร์ด และ `BL` เข้า 3.3 V ตรงๆ เหลือแค่ `SCK` `MOSI` `DC` `CS`

**ขาที่จองไว้ห้ามเอาไปใช้:** GPIO 8, 9 (I2C0 สำหรับ IMU / INA226 ในอนาคต)

> **เมื่อขึ้นเฟส 2** ให้ย้ายจอไปอยู่กับ Pi 5 → ได้ขาคืน 4 ขาไปใส่ IMU / INA226 / cliff sensor พอดี

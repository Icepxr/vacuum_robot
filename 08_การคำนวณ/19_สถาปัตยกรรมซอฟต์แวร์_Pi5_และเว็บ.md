## 19.1 แบนด์วิดท์ภาพสด MJPEG บน Wi-Fi hotspot

**สมมติฐาน**
- ภาพ preview 640×480 · JPEG quality ~75 · ฉากทั่วไป (ไม่ใช่ noise เต็มภาพ) → ขนาดเฟรม **40–60 kB** [ประมาณการ — ค่าทั่วไปของ JPEG ที่ความละเอียดนี้ ยังไม่วัดจากกล้องจริง]
- เฟรมเรต 10 fps (ค่าตั้งต้น) · 15 fps (ถ้าอยากลื่นขึ้น)
- 1 client ดูภาพพร้อมกัน (fan-out จาก encode ครั้งเดียว — ถ้า 2 client แบนด์วิดท์ ×2 แต่ CPU ไม่เพิ่ม)
- throughput จริงของ Wi-Fi hotspot บน Pi 5 (2.4 GHz · ระยะ < 10 m · โล่ง) ≥ **20 Mbps** [ประมาณการ — ไม่มีการวัดในโปรเจกต์ · Pi 5 มี Wi-Fi 5 dual-band แต่สนามแข่งมักแออัดที่ 2.4 GHz จึงใช้ค่าอนุรักษ์นิยม]

**สูตร** `BW = frame_size × fps × 8`

| กรณี | แทนค่า | ผล | เทียบ 20 Mbps | ป้าย |
|---|---|---:|---:|---|
| 10 fps · 40 kB | 40,000 × 10 × 8 | **3.2 Mbps** | headroom 6.3× | [คำนวณ] |
| 10 fps · 60 kB | 60,000 × 10 × 8 | **4.8 Mbps** | headroom 4.2× | [คำนวณ] |
| 15 fps · 60 kB | 60,000 × 15 × 8 | 7.2 Mbps | headroom 2.8× | [คำนวณ] |
| 2 client · 10 fps · 60 kB | 4.8 × 2 | 9.6 Mbps | headroom 2.1× | [คำนวณ] |

**ผลลัพธ์:** 10 fps ปลอดภัยแม้ Wi-Fi ได้แค่ 1/4 ของที่ประมาณ · ถ้ากระตุก ลด fps ก่อน (ลด BW เชิงเส้น) อย่าลดขนาดภาพ (ต้องเห็นตัวเลขมิเตอร์ตอนเล็ง)

## 19.2 แบนด์วิดท์ WebSocket telemetry + คำสั่ง

**สมมติฐาน**
- ข้อความ `tele` เป็น JSON มีคีย์ชื่อยาว (อ่านง่ายกว่าประหยัด byte) ≈ **250–300 B** [ประมาณการ — นับจาก schema ใน software_architecture §4.2 · ยังไม่ได้ serialize จริง]
- อัตรา 20 Hz ตามที่ ESP32 ส่ง `#T` (ไฟล์ 09 §9.5)
- คำสั่ง `drive` ≈ 40 B × 10 Hz

**สูตร** `rate = size × Hz`

```
telemetry ↑ : 300 B × 20 Hz = 6,000 B/s = 48 kbps     [คำนวณ]
drive     ↓ :  40 B × 10 Hz =   400 B/s = 3.2 kbps    [คำนวณ]
รวม ≈ 51 kbps  ≈ 1.1 % ของภาพ MJPEG (4.8 Mbps)
```
**ผลลัพธ์:** ไม่ต้องบีบอัดหรือส่ง binary · ถ้าวันหนึ่งจะถี่กว่า 20 Hz ก็ยังห่างขีดจำกัดมาก

### 19.2a โหลด UART เมื่อเพิ่มคำสั่งจาก Pi (ทวนไฟล์ 09 §9.5)

```
#T 20 Hz × ~90 B          = 1,800 B/s   (เดิม ไฟล์ 09)
$V 10 Hz × ~25 B          =   250 B/s   (ใหม่ — โหมด manual)
#A ตอบ $V 10 Hz × ~12 B   =   120 B/s   (ใหม่)
#E / $K / $C นานๆ ครั้ง   <    50 B/s
รวม ≈ 2,220 B/s   vs 11,520 B/s → headroom 5.2×   (เดิม 6.4×)     [คำนวณ]
```
**ผลลัพธ์:** baud 115200 ยังพอ ไม่ต้องขยับเป็น 460800

## 19.3 Deadman 3 ชั้น — เวลาจนล้อหยุด และระยะไถล

**สมมติฐาน**
- browser ส่ง `drive` ทุก 100 ms · Pi ส่ง `$V` ซ้ำทุก 100 ms (ผ่านเกณฑ์ G8 "≤ 200 ms" ด้วย margin 2×)
- timeout ฝั่ง Pi = 300 ms (ค่าเสนอ · ทน packet หาย 2 ชุดติด) · task `deadman` เดินทุก 50 ms
- G8 ฝั่ง ESP32 = 300 ms (ไฟล์ 09 §9.7) · `T_Comm` เดิน 20 Hz = 50 ms (`system_architecture` §5)
- เมื่อ ESP32 ตัดสินหยุด ล้อหยุดทันที (ไม่คิดระยะเบรกทางกล — G14 จำกัด 0.15 m/s มวล 2.3 kg โมเมนตัมต่ำ)
- ความเร็วสูงสุดเฟส 1 = **0.15 m/s** (G14)

**สูตร** `t_stop = timeout + คาบของตัวตรวจ + คาบของตัวสั่ง` · `d = v × t_stop`

| สถานการณ์ | แทนค่า | t_stop | d = 0.15 × t | ป้าย |
|---|---|---:|---:|---|
| browser หาย → Pi จับได้ | 300 + 50 (deadman tick) + 50 (T_Comm รับ `$S`) | **400 ms** | **60 mm** | [คำนวณ] |
| Pi หาย → ESP32 G8 จับได้ | 300 + 50 (T_Comm tick) | **350 ms** | **53 mm** | [คำนวณ] |
| ทางเลือก: timeout Pi = 200 ms | 200 + 50 + 50 | 300 ms | 45 mm | [คำนวณ] |

**เทียบกับสิ่งที่ระบบยอมรับอยู่แล้ว:** stall-as-bumper ระดับ 1 หน่วง 300 ms → หุ่นดันวัตถุต่อ **45 mm** ที่ 0.15 m/s (`system_architecture` §6.2) → ระยะไถลจาก deadman 53–60 mm อยู่ระดับเดียวกัน ไม่ได้สร้างความเสี่ยงประเภทใหม่

**ผลลัพธ์:** เลือก 300 ms เป็นค่าตั้งต้น · ถ้าอยากได้ 45 mm เท่า stall ให้ใช้ 200 ms แต่จะทน packet หายได้แค่ 1 ชุด — **ยังไม่ตัดสินใจ** (software_architecture §10 ข้อ 4)

> ⚠ ทำไม Pi ต้องเป็นคนส่ง `$V` ซ้ำ ไม่ใช่ forward จาก browser ตรงๆ: Wi-Fi jitter บน LAN ทั่วไป 5–50 ms แต่ spike ระดับ 100–200 ms เกิดได้ [ประมาณการ] ถ้า forward ตรง spike 1 ครั้งก็ทำให้ `$V` เว้นเกิน 200 ms → G8 หลุดทั้งที่ผู้ใช้ยังกดอยู่ → หุ่นกระตุก · ให้ Pi "ถือ" setpoint แล้วส่งซ้ำด้วย timer ของตัวเอง jitter ฝั่ง Wi-Fi จะถูกดูดซับที่ timeout 300 ms แทน

## 19.4 เวลาถ่ายภาพ vs หน้าต่าง `CAMERA_CAPTURE` 5 s

**สมมติฐาน**
- กล้อง CSI ผ่าน picamera2 **เปิดค้างตลอด** 2 stream (main + lores) → AE/AWB นิ่งอยู่แล้ว ไม่ต้องรอ 1.5 s แบบ `grab_picamera2()` เดิม
- `capture_array("main")` ที่ 2304×1296 ≈ **100–300 ms** [ประมาณการ — ขึ้นกับรุ่นกล้องที่ยังไม่เลือก]
- encode + เขียน JPEG ~1–2 MB ลง microSD ≈ **100–200 ms** [ประมาณการ — SD class 10 เขียน ≥ 10 MB/s]
- ส่ง `$K` ผ่าน UART 115200: ~15 B ≈ 1.3 ms (ละได้)
- `T_Comm` รับ `$K` ภายใน 50 ms
- OCR (tesseract บน ROI ที่ crop แล้ว · Pi 5) ≈ **0.3–2 s** [ประมาณการ — ยังไม่เคยรันบน Pi · README ของ 11_pi5_vision ก็ยังไม่เคยรันบนโน้ตบุ๊ก]

**สูตร** `t_ack = t_capture + t_write + t_uart + t_comm_tick` · `margin = 5,000 − t_ack`

```
กรณีดี   : 100 + 100 + 1 + 50 = 251 ms  → margin 4,749 ms (95 %)     [คำนวณ]
กรณีแย่  : 300 + 200 + 1 + 50 = 551 ms  → margin 4,449 ms (89 %)     [คำนวณ]
ถ้าใช้วิธีเดิม (เปิด-ปิดกล้องต่อรูป): + 1,500 ms รอ AE + ~500 ms เปิดกล้อง
           ≈ 2,551 ms → margin 2,449 ms (49 %)                        [คำนวณ]
ถ้ารอ OCR ก่อนตอบ $K (ห้ามทำ): + 300–2,000 ms → กรณีแย่ 2,551 ms หรือมากกว่า
           และถ้า tesseract ค้าง (เกิดได้กับภาพเบลอ) → ชน timeout แน่นอน
```
**ผลลัพธ์:** เปิดกล้องค้าง + ตอบ `$K` ทันทีที่ภาพลง SD → ใช้หน้าต่างแค่ ~5–11 % · OCR ต้องอยู่นอก critical path เสมอ

### 19.4.1 วัดจริง 11 ก.ย. 2026 บน Pi ตัวจริง (Ubuntu 24.04 · Logitech BRIO บน USB 2.0 · OpenCV 4.10 · V4L2 MJPG 1920×1080)

> กล้องจริงเป็น USB ไม่ใช่ CSI (C22 ไฟล์ 10) → สมมติฐาน "picamera2 2 stream" ด้านบน**ไม่ใช้แล้ว** ค่าด้านล่างแทน t_capture/t_write ของ §19.4 · ปิด **V1 บางส่วน** และ **V4**

| รายการ | วิธีวัด | ค่า | ป้าย |

| กล้องเปิดค้าง: `cap.read()` 1080p MJPG | เฉลี่ย 30 เฟรมหลังทิ้ง 10 เฟรม | **เฉลี่ย 61 ms · max 71 ms (≈ 16 fps)** — ต่ำกว่า 30 fps ที่กล้องรายงาน คาดว่าเป็นเวลา decode MJPEG→BGR ของ OpenCV บน CPU [ประมาณการสาเหตุ] | [วัดจริง] |

**แทนค่าใน §19.4 (กล้องเปิดค้าง):**

วิธีเดิมเปิด-ปิดต่อรูป: 1,660 + 14 + 1 + 50 = 1,725 ms → margin 3,275 ms (65 %)  [คำนวณจากค่าวัดจริง]

**ผลลัพธ์:** ดีกว่ากรณีดีที่ประมาณไว้ (251 ms) เพราะ USB MJPG ไม่ต้อง encode ฝั่ง Pi · ยืนยันข้อสรุปเดิม: เปิดกล้องค้าง + `$K` ทันทีที่ลง SD
**ยังค้าง:** V1 ต้องวัดซ้ำจากเฟรมจริงตอนเล็งมิเตอร์ (38.8 kB นี้เป็นภาพห้องนอนกลางคืน) · V5 (OCR) ยังไม่วัด · ถ้าย้าย BRIO ไป USB 3 แล้วได้ 4K ต้องวัด `cap.read()` ใหม่ (decode 4K MJPEG น่าจะ > 150 ms [ประมาณการ]) · Pi ตอนวัดเป็น Ubuntu Desktop มี GNOME รันอยู่ — ค่าอาจดีขึ้นเล็กน้อยถ้าปิด GUI

| รายการ | ค่า | ป้าย |

## 19.5 Latency คำสั่งขับจาก browser ถึงล้อ

**สมมติฐาน**
- WS บน LAN: 5–20 ms [ประมาณการ]
- Pi: event loop ว่าง → เขียน UART ทันที · แต่ `$V` ถูกส่งตาม timer 100 ms → รอเฉลี่ย 50 ms, สูงสุด 100 ms
- UART 25 B ที่ 11,520 B/s ≈ 2.2 ms
- ESP32: `T_Comm` 50 ms → `T_Behavior` 50 ms → `T_Control` 10 ms (คาบจาก `system_architecture` §5; worst case = รอเต็มคาบทุกชั้น)

**สูตร** ผลรวมของแต่ละช่วง

```
typical : 10 + 50 + 2 + 25 + 25 + 5   ≈ 117 ms    [คำนวณ]
worst   : 20 + 100 + 2 + 50 + 50 + 10 ≈ 232 ms    [คำนวณ]
ระยะที่หุ่นวิ่งไปก่อนคำสั่งมีผล ที่ 0.15 m/s : 18–35 mm
```
**ผลลัพธ์:** พอสำหรับบังคับด้วยมือที่ 0.15 m/s · ถ้าอยากไวขึ้น จุดที่ลดได้มากสุดคือให้ Pi ส่ง `$V` **ทันทีที่ค่าเปลี่ยน** แล้วค่อยส่งซ้ำตาม timer (ตัด 50–100 ms) — ไม่กระทบ deadman

## 19.7 ค่าตั้งต้นของภารกิจ 1 รอบแบบ script (ขั้น D · `src/robot/mission_core.h`) — 15 ก.ย. 2026

### 19.7.1 duty ล้อที่ให้ ≈ 0.15 m/s (G14)

**สมมติฐาน**
- rpm เพลาออกที่ duty 100 % ไร้โหลด = **152 rpm** [วัดจริง M1 · ไฟล์ 15] — ผ่าน L298N ที่ตกคร่อม 1.71 V; DRV8871 จะได้สูงกว่านี้เล็กน้อย
- ล้อ **Ø90 mm** (C24 — ไม่ใช่ 65 mm ที่ยังค้างใน config.h)
- rpm ∝ duty เชิงเส้นโดยประมาณ [ประมาณการ — มอเตอร์ DC ไร้โหลด]
- มีโหลดจริง (น้ำหนักหุ่น 30 N · พรม) จะช้ากว่านี้ [ยังไม่วัด]

**สูตร** `v = rpm/60 × π × D` · `duty = v_target / v_100%`

```
v_100% = 152/60 × π × 0.090 = 0.716 m/s                                [คำนวณจากค่าวัดจริง]
duty   = 0.15 / 0.716 = 0.209 → 210 ‰                                  [คำนวณ]
(ถ้ายังใช้ D = 65 mm ผิดๆ: v_100% = 0.517 m/s → 290 ‰ — เร็วเกิน G14 38 % บนล้อจริง)
```
**ผลลัพธ์:** ค่าตั้งต้น `drive_permille` ใน `mission_core.h` = **210** [คำนวณ] · ปรับหน้างานด้วย `mis set drive` · ยังไม่มี PID/odometry ดังนั้น "0.15 m/s" เป็นค่าไร้โหลด ของจริงช้ากว่า (ปลอดภัยฝั่งช้า)

### 19.7.2 เวลาต่อจุดมิเตอร์ vs ภารกิจ 3 นาที

**สมมติฐาน** — ค่าใน `MissionCfg`: r2 1.0 s · drive 5 s [ประมาณการ] · stop_settle 0.5 s · settle 2 s · capture ~0.1 s [วัดจริง 71 ms] · slew เซอร์โว 417 us/s [โมดูล servo] → ยก/พับ **เต็มช่วง 2000 us = 4.8 s ต่อทาง** (ถ้าช่วงจริงสั้นกว่า เช่น 1000 us → 2.4 s)

```
t_จุด (เต็มช่วง) = 1.0 + 5.0 + 0.5 + 4.8 + 2.0 + 0.1 + 4.8 = 18.2 s                [คำนวณ]
3 จุด = 54.6 s · 4 จุด = 72.8 s   → เหลือจาก 180 s อีก ≥ 107 s สำหรับวิ่งจริง/หลบ  [คำนวณ]
สัดส่วนเวลาที่เสียไปกับเสา (ยก+นิ่ง+พับ) = 11.6/18.2 = 64 % ของทุกจุด               [คำนวณ]
```
**ผลลัพธ์:** ภารกิจ 3–4 จุดพอดีในกรอบ 3 นาที **ถ้าระยะระหว่างมิเตอร์วิ่งได้ใน ~5 s** (0.75 m ที่ 0.15 m/s) — สนาม 100×250 cm น่าจะพอ [ประมาณการ] · จุดที่ลดได้มากสุดคือ slew เซอร์โว: ถ้าช่วงยกจริง ≤ 1000 us จะประหยัด 4.8 s/จุด

## 19.8 หน่วงรวมตอนขับจริง "ตาเห็น → ล้อหยุด" และกรณีค้าง/WDT — 16 ก.ย. 2026 (หลัง C28/C29)

ทวน §19.3/§19.5 ด้วยค่าที่**วัดจริงวันนี้**แทนสมมติฐาน แล้วขยายให้ครอบคลุมภาพสด + คน + ramp และเพดานความเร็วที่ผู้ใช้ตั้งได้ (C28)

### 19.8.1 ค่าที่วัดได้ 16 ก.ย. (Pi จริง · ESP32 จริง · Mac ↔ Pi บน Wi-Fi อาคาร `JumboPlus` — **ยังไม่ใช่ hotspot**)

### 19.8.2 โซ่หน่วง "เห็นสิ่งกีดขวาง → ล้อหยุดสนิท"

**สมมติฐาน**
- ภาพสด 10 fps · เฟรมที่ thread ถืออยู่มีอายุเฉลี่ยครึ่งคาบ `cap.read` (61 ms) ≈ 30 ms, แย่สุด 61
- เบราว์เซอร์ decode + วาด 1–2 เฟรมจอ 60 Hz = 16–33 ms [ประมาณการ]
- คนตอบสนองต่อภาพแบบง่าย 250 ms · แบบต้องตัดสินใจ 400 ms [ประมาณการ — ค่าทั่วไป ยังไม่วัดกับคนขับจริง]
- ปล่อยจอย → `pump()` เห็นตอน tick ถัดไป (0–100 ms, เฉลี่ย 50) → `release` → Pi ส่ง `$S` **ทันที** (ไม่รอ timer) → ESP32 ≤10 ms
- ESP32 ไล่ duty ลง 15 ‰/10 ms (slew) แล้ว `brake()` ที่ 0 · ความเร็ว ∝ duty · ไม่คิดไถลหลังเบรก (เกียร์ JGB37 back-drive ฝืด [ประมาณการ])
- duty = v × 1400 ‰/(m/s) (§19.7.1)

**สูตร**
```
t_video  = อายุเฟรม + เฟรมแรก(วัด) + วาด
t_human  = 250 / 400 ms
t_cmd    = pump + WS ทางเดียว(≈ RTT/2) + UART+ESP32 (10)
t_ramp   = duty / 15 ‰ × 10 ms
d_stop   = v × (t_video + t_human + t_cmd) + v × t_ramp / 2
```

**แทนค่า**
```
t_video  typ = 30 + 116 + 16 = 162 ms      p90 = 61 + 165 + 33 = 259 ms
t_cmd    typ = 50 +   8 + 10 =  68 ms      p90 = 100 + 34 + 11 = 145 ms
รวมก่อน ramp typ = 162 + 250 + 68 = 480 ms   p90 = 259 + 400 + 145 = 804 ms

t_ramp: 150 mm/s → 210 ‰ → 140 ms · 300 → 420 ‰ → 280 ms · 500 → 700 ‰ → 467 ms · 716 → 1000 ‰ → 667 ms
```

| เพดานที่ตั้ง (mm/s) | d ระหว่างรอ typ / p90 | d ระหว่าง ramp | **d_stop typ** | **d_stop p90** | ป้าย |
|---:|---:|---:|---:|---:|---|
| **150** (เริ่มต้น) | 72 / 121 | 11 | **~85 mm** | **~130 mm** | [คำนวณจากค่าวัดจริง + คน ประมาณการ] |
| 300 | 144 / 241 | 42 | **~185 mm** | **~285 mm** | " |
| 500 | 240 / 402 | 117 | **~355 mm** | **~520 mm** | " |
| 716 (ฮาร์ดแวร์) | 344 / 576 | 239 | **~585 mm** | **~815 mm** | " |

**ผลลัพธ์:** ที่ 150 mm/s หุ่นวิ่งต่อ ~1 ช่วงล้อ (Ø90) หลังตาเห็น · ที่ 300 ~2–3 ช่วงล้อ · ที่เพดานฮาร์ดแวร์เกือบ 1 m — ตัวเลข "~15–20 cm ที่ 300" บนสไลเดอร์ (C28) ตรงกับ typ · **ตัวที่กินเวลามากสุดคือคน (250–400) ไม่ใช่ระบบ (230–400)** — ลดฝั่งระบบได้อีกอย่างมาก ~100 ms (fps 15 + ส่ง `$V` ทันที) แต่ลดฝั่งคนไม่ได้
**ข้อสังเกต:** ramp ลงกลายเป็นก้อนใหญ่เมื่อเร็ว (239 mm ที่ 716) — ถ้าจะเปิดเพดานสูงจริง ควรให้ `$S` ใช้ slew ลงเร็วกว่าขาขึ้น (เช่น 60 ‰/tick → 1000 ‰ ใน 167 ms) หรือ brake ทันทีเหมือน `$E` — **ยังไม่ตัดสินใจ**

### 19.8.3 ทวน deadman (§19.3) ด้วยค่าวัดจริง

```
browser หาย → Pi: 300 (timeout) + 0–100 (drive_loop tick, เฉลี่ย 50) + 10 (ESP32) = 360 typ / 410 max → + ramp 140
   d ที่ 150 mm/s = 0.15 × 0.41 + 10.5 = 72 mm            (เดิม §19.3: 60 mm — เพิ่มเพราะนับ ramp)   [คำนวณ]
Pi หาย → ESP32 G8: 300 + 10 = 310 → + ramp 140 → d = 47 + 10.5 = 57 mm                          (เดิม 53)   [คำนวณ]
ที่ 716 mm/s: browser หาย = 0.716 × 0.41 + 239 = 533 mm · Pi หาย = 222 + 239 = 461 mm                       [คำนวณ]
```

### 19.8.4 กรณี loop() ค้าง (C29 ก่อนแก้) และผลของ task WDT

```
ไม่มี WDT:  ล้อค้าง duty เดิมตลอดที่ค้าง (C29 วัดได้ 2.0 s) → d = v × 2.0 = 300 mm ที่ 150 · 1,432 mm ที่ 716   [คำนวณจากค่าวัดจริง]
มี WDT 1 s: ค้าง 1.0 s → รีเซ็ต → GPIO ลอย → DRV8871 coast (pulldown ในตัว [สเปก]) → ล้อฟรี
            d ก่อน coast = v × 1.0 = 150 mm ที่ 150 · 716 mm ที่ 716 (+ ไถล coast ยังไม่วัด)
            ตาบอด = 1.0 (WDT) + 2.04 (บูต วัดจริง) ≈ 3.0 s → Pi ยังส่ง $V ซ้ำอยู่ → ขับต่อเองหลังบูต
ถ้าตัด delay(2000) ใน env robot: บูต ≈ 2036 − 2000 = ~40 ms + bootloader (ไม่ได้แยกวัด) → ตาบอดรวม ≈ 1.1–1.3 s   [คำนวณ · ต้องวัดซ้ำ]
```
**ผลลัพธ์:** WDT 1 s ลดระยะวิ่งค้างจาก 300 → 150 mm ที่เพดานเริ่มต้น และจากไม่จำกัด (ค้างนานกว่านั้นก็ได้) → จำกัดที่ 1 s เสมอ · `delay(2000)` ในเฟิร์มแวร์รวมเป็นค่าใช้จ่ายที่ไม่จำเป็นบนหุ่น (มีไว้ให้คอนโซล USB เห็นบรรทัดแรก) → **ควรตัดออกหรือเหลือ 100 ms** ก่อนใส่ WDT

**ทำแล้ว + วัดจริง 16 ก.ย. 2026 (V18 ปิด):** ตัด `delay(2000)` · `src/robot/wdt.h` task WDT 1000 ms เฝ้า loopTask ตัวเดียว (deinit ของ core 5 s/idle ก่อน) · `#E BOOT,<reason>` ตอนบูต · คำสั่งคอนโซล `hang <ms>` busy-wait เพื่อทดสอบ

| การทดสอบ | ผล | ป้าย |
|---|---|---|
| รีเซ็ต (DTR/RTS) → `#E BOOT` / `#T` แรก | **31 ms / ~40 ms** (เดิม 2,040 ms) | [วัดจริง] |
| `$P` → `#A` ขณะ WDT เปิด | 11 ms (ไม่เปลี่ยน) | [วัดจริง] |
| `hang 500` (< timeout) | `#T` เว้น 0.51 s แล้วเดินต่อ **ไม่รีบูต** · 10 เฟรม/1.5 s | [วัดจริง] |
| `hang 3000` (> timeout) | "Task watchdog got triggered — loopTask (CPU 1)" ที่ **1.003 s** → รีบูต → `#E BOOT,TASK_WDT` ที่ **1.382 s** → `#T` กลับมาที่ **1.442 s** | [วัดจริง] |

```
ตาบอดรวมเมื่อค้าง = 1.00 (WDT) + 0.44 (panic print + บูต) = 1.44 s   (เดิมคาด 3.0 s · หลังตัด delay คาด 1.1–1.3)   [วัดจริง]
ระยะวิ่งค้างสูงสุด = v × 1.0 s (ก่อน coast) → 150 mm ที่เพดานเริ่มต้น · 716 mm ที่ฮาร์ดแวร์                          [คำนวณจากค่าวัดจริง]
```
Pi ฝั่งรับ: เห็น `#E BOOT` → ส่ง `$L` ซ้ำอัตโนมัติ (เพดานอยู่ใน RAM ของ ESP32) + log เตือน "รีบูตจาก watchdog" (test `test_boot_event_resends_limits`)
ข้อสังเกต: ROM bootloader พิมพ์ `rst:0xc (RTC_SW_CPU_RST)…` ออก UART0 ขาเดียวกับลิงก์ Pi — daemon ทิ้งเป็น bad line อยู่แล้ว (นับใน `stats`) ไม่กระทบ
ยังไม่ครอบคลุม: ค้างที่*ไม่ใช่* loopTask (เช่น task ของ USB/Wi-Fi) · ชุดทดสอบคอนโซล (`m t1`, `bl sweep` …) รันใต้ `wdtSuspend()` โดยตั้งใจ — ห้ามใช้ตอนหุ่นวิ่ง

### 19.8.5 หน่วงตอน "ออกตัว" (ดันจอย → ความเร็วเต็ม) — ฟีลการขับ

```
pump tick 0–100 + ramp ฝั่ง browser (first-order τ = rampMs 250 → 63 % ที่ 250, 95 % ที่ 750 ms)
+ WS 8 + Pi drive_loop timer 0–100 (ส่งตาม timer ไม่ใช่ทันที) + UART/ESP32 12 + slew 140 (ที่ 150) + deadband 40 ‰ (≈ 29 mm/s แรกล้อไม่ขยับ)
→ ล้อเริ่มขยับ ≈ 0.2–0.35 s หลังดันจอย · ถึง 95 % ≈ 1.0 s                                                    [คำนวณ]
```
**ผลลัพธ์:** ความหน่วงออกตัวถูกกำหนดโดย `rampMs` ของผู้ใช้เป็นหลัก (ตั้ง 0 ได้ในแท็บขับ → เหลือ ~0.3–0.45 s) · ระบบเองมี 2 จุดลดได้: Pi ส่ง `$V` ทันทีที่ค่าเปลี่ยน (−50 ms เฉลี่ย) และ slew ขึ้นเร็วกว่านี้ (แลกกับกระชาก/กระแส inrush ที่ยังไม่วัด)
